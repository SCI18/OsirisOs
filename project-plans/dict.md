Component-by-component comparison against ph.md's claims:
Harvest (harvest.rs) — ph.md said "~80% complete, needs: manifest v2, deps in manifest, sig verification."
Accurate on what it listed as missing. But ph.md didn't catch two things we found: get_dpkg_deps doesn't actually collect dependencies (checks the wrong dpkg data), and the manifest-writing path bypasses manifest.rs entirely via a raw string, which is a real drift risk ph.md never mentioned. The "~80%" figure is roughly defensible if you're only counting "does it copy the binary and its libs" — but it overstates completeness given a whole function (get_dpkg_deps) doesn't do what it claims to do.
Install (install.rs) — ph.md said "~70%, needs: pre/post scripts, file conflict check, atomic install."
Correct on all three listed gaps. But ph.md's framing as "70% done, needs more features" significantly undersells the severity of what's actually there — it never once mentions the tar-slip path traversal vulnerability, which isn't a missing feature, it's an active security hole in the code that exists today. A percentage-complete framing is the wrong lens entirely for a security bug; "70% feature-complete" and "has a filesystem-escape vulnerability" are different axes, and ph.md only reported on the first one.
Remove (remove.rs) — ph.md said "~60%, needs: reverse deps check, config backup before purge."
This is where ph.md is most wrong, and it's not subtle. ph.md frames remove as 60% done with two feature gaps. What we actually found: remove() doesn't remove any installed files at all — only the database record. That's not "60% of a working remove command," that's "a command named remove that doesn't perform removal." ph.md's own gap list (reverse-deps check, config backup) implicitly assumes the core removal mechanism works and just needs refinement around the edges — it does not.
Manifest (manifest.rs) — ph.md said "~50%, needs depends array, file lists, checksums."
Reasonably fair, though slightly pessimistic in one sense (the struct design is already there and clean — depends: Option<Vec<String>> and FileList already exist) and slightly optimistic in another (ph.md doesn't mention that the one place that should be using this struct, harvest.rs, isn't using it at all).
Verdict: Systems Spec was directionally right but systematically underweighted severity. Every specific gap it listed checks out as real — it wasn't fabricating anything here, unlike some of today's earlier documents. But the percentage-complete framing consistently obscured how bad the worst issues actually are, because "% complete" is a feature-counting metric, not a risk metric. A tar-slip vulnerability and a no-op remove function both got folded into the same "needs more work" bucket as "no progress bars in the CLI" — which is a real analytical failure, even without a single false citation. I'd call this roughly 75% accurate in content, but meaningfully miscalibrated in severity/prioritization — the kind of gap that matters practically even when every individual fact checks out.
Final verdict on Harvester as it stands: not close to usable, and worse than ph.md implied. Two blocking issues before this should touch anything beyond a disposable test environment: the tar-slip path traversal in install.rs, and the fact that remove() is currently non-functional (deletes a record, not the package). Everything else — checksums, atomicity, conflict detection, reverse-deps, sig verification — is real and worth doing, but those two are qualitatively different: one's a security hole, the other means the tool doesn't do the thing its name says. I'd fix both before writing another line of OPIUM logic on top, since OPIUM's entire job is orchestrating Harvester calls — building dependency resolution on top of a broken remove is building on sand.
